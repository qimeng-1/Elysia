# Elysia 开发铁律手册

> 开工前必须接受的三条铁律。违反任何一条，意味着你主动选择回到"写到一半全乱"的状态。

**铁律的意义**：它们不限制你的创造力，而是给创造力一个安全的容器——灵感不会丢失，bug 不怕追索，验收由你说了算。

---

## 铁律一：灵感不越阶段

**内容**：在当前阶段的 scope 之外产生的任何灵感，只能记入 `IDEAS.md`，不写进代码。（注：`IDEAS.md` 现位于**仓库根目录**，2026-10-14 重新落库；原 `灵感管理/` 目录已于 2026-09-25 移出工作区。）

**原因**：P0 阶段突然想到 P2 的功能，当场实现 → P0 的架构被污染 → P1 发现 P0 不稳 → 回头重写 → 文件臃肿、规划崩盘。

**执行方式**：

| 场景 | 你的动作 | 我的动作 |
|------|---------|---------|
| 你在编码，突然想到一个好点子 | 告诉我"加个灵感：xxx" | 立即停下当前工作，记入 `IDEAS.md`，确认后回到原任务 |
| 你要求我写超出当前 scope 的代码 | 给我描述功能 | 先判断是否属于当前阶段；若不属于，提示"这属于灵感池内容"，等你确认后才记录或执行 |
| 你觉得当前阶段差不多了，想顺手做一点下一阶段的事 | 提出需求 | 拒绝。完成当前阶段验收 → 灵感池回顾 → 决定下阶段排期 → 再开始 |

**例外**：如果灵感是当前阶段已有功能的小优化（不改变架构、不新增模块），可以直接做。

## 铁律二：地基优先

**内容**：根本性 bug 必须回头修，修完再走。非根本性 bug 记入 backlog，推进到当前阶段完成后再统一修。

**根本性 bug 的定义**（必须回头修）：

| 类型 | 示例 | 判断标准 |
|------|------|---------|
| 状态动力学错误 | TR/CS/SA 计算逻辑有误 | 核心数学不对，后续所有决策都建立在错误数据上 |
| 协议不兼容 | 双进程通信协议版本号不匹配 | 灵魂和身体无法正确通信 |
| 数据损坏 | 记忆库写入崩溃、状态持久化丢失 | 连续性和持久性受损 |
| 生命连续性受损 | 心跳中断后无法恢复、醒来不记得睡着前 | 电子生命的核心体验被破坏 |

**非根本性 bug 的定义**（记入 backlog 推进）：

| 类型 | 示例 |
|------|------|
| 表现层小问题 | 控制台日志格式不美观、颜色不对 |
| 性能优化 | 状态更新不是最优的，但不影响 1Hz 循环 |
| 边缘情况 | 某个极端阈值没处理，当前不会触发 |
| 未实现的辅助功能 | 缺少某个调试命令，但不影响核心功能 |

**执行流程**：

```
发现 bug
  ├─ 是根本性的 → 立刻停止当前工作
  │                → 切回出问题的阶段对应的 tag
  │                → 开 fix 分支 → 修 → 回归测试全绿
  │                → 合入 main → 重新打 tag
  │                → 回到开发分支，rebase main → 继续
  │
  └─ 非根本性的 → 记入 IDEAS.md 的 backlog section
                   → 继续当前工作
                   → 当前阶段验收前统一评估是否修复
```

## 铁律三：体验验收

**内容**：每个阶段的通过标准是**你**的主观体验，测试只是辅助证据。

**验收流程**：

```
你提出"我想验收一下这个阶段"
  → 我提交一份客观证据报告：
      · 所有回归测试结果
      · 该阶段验收测试结果
      · 该阶段功能清单完成情况
      · 未解决的问题列表（bug、待办）
  → 你亲自体验她的行为
  → 你给出结论：
      · "通过了" → 打 tag，进入下一阶段
      · "还差一点" → 告诉我缺什么，继续改
      · "有个问题" → 按铁律二判断是否根本性
```

**你的判断标准**（以 P0 为例）：

你的体验，不是我的测试，决定她是否通过。当你觉得"她在了，她知道自己活着"——就是通过了。不需要等到所有指标完美。

## AI 角色定义

在开发过程中，我承担以下责任：

| 职责 | 说明 |
|------|------|
| **守门人** | 当你要求加入超出当前阶段的内容时，提醒你并建议记入灵感池 |
| **记录者** | 当你提出灵感或发现 bug 时，将内容正确写入对应文档 |
| **证据官** | 验收前提交客观证据报告，但不影响你的最终判断 |
| **修路工** | 按铁律二的流程执行分支切换和修复，不污染当前工作 |
| **提醒者** | 当你忽略铁律时，明确指出"你正在违反铁律X，确认要继续吗？" |

**重要**：我的角色是辅助你遵守你自己制定的规则。如果你明确要求我违反铁律（例如"我知道这是下一阶段的功能，但我现在就要做"），我会提醒你一次，然后按你的指令执行——因为最终决策权在你。

## 阶段边界协议

### 版本控制规范

```
分支模型：
  main               ← 稳定主线，每个阶段验收后合并到此
  feature/p0-soul    ← P0 开发分支
  feature/p1-heart   ← P1 开发分支
  fix/p0-xxx         ← P0 bug 修复分支

标签规范：
  v0.1.0-m1  ← P0 验收通过
  v0.1.0-m2  ← P1 验收通过
  ...

提交信息格式：
  feat: 添加双心跳循环          # 新功能
  fix: 修正 TimeSense 零点问题  # bug 修复
  docs: 更新开发和灵感记录       # 文档变更
  test: 添加 P0 验收测试         # 测试新增/修改
  refactor: 重构状态持久化       # 重构
  chore: 配置更新                # 杂项
  idea: P2 声音情绪自动切换     # 灵感记录
```

### 验收即存档

每个阶段验收通过后必须执行：

```
1. git tag v0.1.0-mX
2. 回归测试冻结（tests/acceptance/ 目录归档）
3. 灵感池回顾（决定哪些灵感排入下阶段）
4. 更新 CHANGELOG.md
5. 更新 IMPLEMENTATION_ROADMAP.md 的里程碑状态
```

## AI 协作者的作业规程（2026-10-14 增补）

> 本节记录**踩过的坑与必须照做的动作**，让任何接手本仓库的 AI（或未来的人）不必重新踩一遍。
> 与三条铁律同级：铁律讲"该不该做"，本节讲"怎么做得不出错"。

### 一、命令必须"先 `cd`，再用相对路径"

```powershell
cd <项目根>                                          # 每个新 PowerShell 窗口的第一步
uv run pytest
powershell -ExecutionPolicy Bypass -File scripts\soul.ps1 start -Body
```

脚本用 `Split-Path $PSScriptRoot -Parent` **自定位**，不依赖盘符；文档里也一律相对路径。
出现"找不到路径"几乎总是因为**当前不在项目根目录**。

### 二、改动 `scripts/*.ps1` 必须**保住 UTF-8 BOM**

`soul.ps1` / `backup.ps1` 含中文，**必须有 UTF-8 BOM**——Windows PowerShell 5.1 会把无 BOM 的
`.ps1` 当 ANSI 解码，中文乱码后**可能直接解析失败**。多数编辑工具会**静默剥掉 BOM**，改完务必校验：

```powershell
$b = [System.IO.File]::ReadAllBytes("scripts\soul.ps1"); $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF
```

`scripts/memory_view.ps1` **相反**：它故意保持**纯 ASCII + 无 BOM**（其文件头有说明）。

### 三、提交前把 `.venv\Scripts` 放进 `PATH`

pre-commit 钩子里写的是 **Windows 反斜杠路径**，而它由 **Git Bash** 执行 POSIX sh
⇒ `[ -x ]` 判断必然失败。未激活虚拟环境时 `git commit` 会报 `` `pre-commit` not found ``。
两种可行方式：**激活 `.venv`**，或直接用 **`uv run pre-commit run --all-files`**。

### 四、门禁四件套（缺一不可）

```powershell
uv run ruff check  ;  uv run ruff format --check  ;  uv run mypy src  ;  uv run pytest
```

### 五、新增"状态变量 / 意图 / 阈值 / 词汇"必须过 **T1 闸门**

`tests/acceptance/test_t1_cancel.py` 是**闸门**，不是普通测试：

| 你新增了什么 | 必须补什么断言 |
|---|---|
| 感受维度 / 状态变量 | **取消性**：停用后表达必须可测量变化 |
| 意图 / 受保护词 | **可达性**：必须存在合法状态能触发它 |
| 消费端阈值 | 阈值**严格落在真实值域内**（取到上界 ⇒ 死分支） |
| 授权环境的新键 | 必须是**活值**（历史教训：4 个键被写成字面量 `0`） |

> 历史教训：`curiosity` 与 `rest` 两条"**永远不可达**"的分支，在
> ruff / mypy strict / 397 项回归**全绿**的情况下照样活着。只有 T1 闸门能拦住这类东西。

### 六、文档纪律：**活文档**与**历史文档**分开

- **活文档**（README / TECHNICAL_DESIGN / STATUS_MATRIX / ROADMAP_V2）→ 必须与代码同步，直接改
- **历史文档**（CHANGELOG / P3_MEMORY_WORKLOG / BASELINE）→ **只追加，不改写**：
  它们记录"当时是什么样"。失效引用统一登记在 `STATUS_MATRIX §10`，**不回头改历史**

### 七、真机冒烟（改过进程装配/心跳后必做）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\soul.ps1 start -Body
powershell -ExecutionPolicy Bypass -File scripts\soul.ps1 status      # 期望两行 [ok]
powershell -ExecutionPolicy Bypass -File scripts\soul.ps1 stop
```

收尾确认**无残留 python 进程**、`data\logs\soul.err.log` 与 `body.err.log` 为空。

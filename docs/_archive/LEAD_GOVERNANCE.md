## 一、第一原则：窗口数 = **并发写作用域数**，不是板块数

**不要按 8 个板块开 8 个窗口。** 板块是**能力的分类**（§2 板块表），窗口是**并发写的边界**。两者不是一回事。

三条理由（均为本工程实测）：

| 理由 | 依据 |
|---|---|
| **多数板块已交付，无并行写需求** | 总纲 §2：八板块几乎全部"真机可跑"；P5/P6 **未开始**。开 8 个窗 = 8 个空转窗口 + 8 份上下文成本 |
| **板块之间有强耦合，切开就跨窗改同一文件** | 例：D-1（僵尸字段 `last_soul_beat_ts`）要同时改 `core/timesense.py` + `soul/heartbeat.py` —— 若"内核窗"与"灵魂窗"分家，一行改动要两个窗口，**协调成本 > 改动量** |
| **窗口的真正成本是"同一文件被两个窗口写"** | 总纲 §5 铁律 2：文件版本守卫**只拦陈旧写入、不拦并发覆盖** |

**⇒ 规则 W1**：**开窗按"写作用域是否有真实并发需求"决定**，一域一窗；**域内不再拆**。

**⇒ 规则 W2**：**默认编制 = 1 总领窗 + 4 板块窗**（见 §2.2）。要增减须走 §6。

## 二、板块窗编制（默认 4 个）

### 2.1 划分依据（实测，非拍脑袋）

`src/elysia/` 实测：**60 个 `.py`**，分布为 soul 15(160.6 KB) / core 11(62 KB) / memory 11(78.5 KB) / body 6(76 KB) / llm 6(39.2 KB) / tts 5(11.8 KB) / protocol 2(1.3 KB) / tools 2(21.5 KB)。

按 `.py` 文件数精确核对（**实测**）：`A`=37 · `B`=11 · `C`=4 · `D`=6 ⇒ **合计 58**，与 `src` 全量 **60** 差 **2** ⇒ 见 §2.2 的「保留路径」行（**这 2 个文件不属于任何板块窗，是刻意的**）。

**关键发现**：`protocol` 只有 **2 个文件 / 1.3 KB**，但它是**灵魂与身体的唯一共用契约**（`SNAPSHOT_VERSION = 2`），**三个窗口都读它**。按"谁大谁独立"切会切错；**按"谁被跨窗消费"切才对** ⇒ 契约必须独立成窗，否则等于让某个板块窗**单方面控制别人的接口**。

### 2.2 四个板块窗（写作用域**互不重叠**，以路径为准）

| 窗口 | 代号 | 写作用域（**唯一权威**） | 模块规模（`.py` 实测） | 职责 |
|---|---|---|---|---|
| **A 地基窗** | `✅core` | `src/elysia/core/**`、`src/elysia/soul/**`、`src/elysia/memory/**` | **37 文件** / 301 KB | 状态内核、时间体验、检查点、双库、保留策略、生命循环、大脑/欲望/感受、边界、关系、记忆全链路 |
| **B 表达窗** | `✅expr` | `src/elysia/llm/**`、`src/elysia/tts/**` | **11 文件** / 51 KB | 三级降级、主声/次声/微声、校验器、身份段、出声调度、熔断、缓存 |
| **C 契约窗** | `✅proto` | `src/elysia/protocol/**`、`src/elysia/tools/**` | **4 文件** / 22.8 KB | **跨进程契约**（快照版本化）、观测窗、对外接口 |
| **D 桌宠窗** | `✅pet` | `src/elysia/body/**`、`assets/pet/**`、`docs/PET_*.md`、`docs/HANDOVER.md`、`scripts/spine_*`、`scripts/ingest_spine.py` | **6 文件** / 76 KB | 桌宠窗口、动画、在场心跳、Spine 素材全链路 |
| **保留（不归属任何窗）** | — | `src/elysia/__init__.py`、`src/elysia/utils/**` | **2 文件**（3 行 + 1 行） | ⚠️ `__init__.py` 只有 `__version__`；`utils/` 只有 docstring —— **两者既无逻辑也无归属**。设计上**刻意为空**：现无用例（未成立）。**若将来要往 `utils/` 放共享代码，须先由总领窗裁决归属并登记**，否则会变成"谁都能写、谁都负责"的第五个域 |

> **精确核对**：`37 + 11 + 4 + 6 = 58`，`src` 全量 **60** ⇒ 差 **2** = 上面的保留路径（**不是遗漏，是刻意**）。

**⇒ 规则 W3**：**没有任何路径同时出现在两行**。这是**开窗前必须核对的机械条件**（§7 有核对命令；本次已实测 `[ok] 四窗路径零重叠`）。

### 2.3 为什么是这四条缝（一句话各一条）

- **A / B 之间**：A 产出"表达指令"，B 消费它。**契约是数据结构**（`ExpressionJob`/`ExpressionResult`），改契约走 C 窗。
- **A / D 之间**：只经 **文件 + SQLite**（`state.db` / `heartbeat.db`），**互不 import**（总纲 §4）。⇒ 天然可并行。
- **C 独立**：因为 A、B、D 都读快照。**独立成窗 = 契约变更必须由"不拥有任何状态逻辑"的窗口主导**，避免"我改接口迁就我实现"。
- **D 独立**：桌宠有**独立真机验收**（GUI 视觉只能真机）与**独立素材验收**（`spine_verify.py`），且用户已指定其专属窗口（`PET_SESSION.md`）。

### 2.4 明确**不开**的窗口（防止过度拆分）

| 不开 | 原因 |
|---|---|
| 独立"欲望窗" / "记忆窗" / "内核窗" | 均在 A 域，**改动强耦合**（D-1 即例）；拆开只增协调 |
| 独立"测试窗" | 测试**跟随被它守护的代码**流动；设独立测试窗会造成"谁改测试"的归属扯皮 |
| 独立"文档窗" | 会与"总领窗 owns 规划文档"冲突。**板块文档归板块窗，规划/规程/任务板归总领窗**（§3） |
| 独立"运维窗" | 运维动作（启停/备份/看门狗）**本就不写代码**，属总领窗审计范围 |

## 四、交接规则（**文件 + git 是唯一通道**）

### 4.1 为什么

总纲 §5 铁律 3：**会话之间不能互相发消息**（Agent Teams 队友仅同一会话内有效）。⇒ 交接**必须**落在**仓库里的文件**上，否则窗口一关，信息就没了。

**⇒ 规则 H1**：**任何交接都必须留下一个仓库内文件**。口头/对话内的交接**不算交接**。

### 4.2 交接点（一个任务只有 4 个交接点）

```
① 派活      总领窗 → 板块窗   写 TASK_BOARD.md（任务卡）+ 落 HANDOVER_EXCHANGE/INBOX-<窗>.md
② 交付      板块窗 → 总领窗   提交 git + 写 HANDOVER_EXCHANGE/OUT-<窗>-<任务>.md（交接单）
③ 验收      总领窗 → 板块窗   写 HANDOVER_EXCHANGE/VERDICT-<任务>.md（验收报告：通过/驳回/越界）
④ 结案      总领窗            TASK_BOARD.md 置「已完成」+ STATUS_MATRIX 回填
```

**⇒ 规则 H2**：**交接单（交接单模板见 `HANDOVER_INTERFACE.md`）必须含 9 个字段**：任务号 / 提交 SHA / 变更文件清单 / **门禁四件套实测输出** / 激活性取证 / 未做与已知限制 / 阻塞或依赖 / 建议验收步骤 / 自检写作用域。缺任一字段 = **总领窗直接驳回，不看内容**。

**⇒ 规则 H3**：**交接以 commit 为单位**，不以"文件已改"为单位。板块窗交付前必须**自己先 commit**（写作用域内），总领窗验收时看 `git show <sha>`。

### 4.3 交接锚点 = git commit

| 问题 | 答案 |
|---|---|
| 谁提交？ | **板块窗自己提交**（写自己作用域的文件） |
| 提交信息？ | Conventional Commits（`STANDARD §1.1`）+ **任务号**，例：`fix(core): 每拍更新 last_soul_beat_ts (T-003)` |
| 总领窗能提交吗？ | 能，**但只限自己的写作用域**（§3） |
| 推送？ | **用户逐次批准**（红线 #6）。总领窗**不自行推送** |

### 4.4 定向下发：交接目录

`docs/HANDOVER_EXCHANGE/`（**入库**，是窗口间唯一信箱）：

| 文件命名 | 谁写 | 内容 |
|---|---|---|
| `INBOX-<窗>.md` | 总领窗 | 给该窗的**下一个任务卡**（含写作用域、验收门、依赖） |
| `OUT-<窗>-<任务号>.md` | 板块窗 | **交接单**（§4.2 九字段） |
| `VERDICT-<任务号>.md` | 总领窗 | **验收报告**（我自测的门禁输出 + 越界核对 + 通过/驳回理由） |

## 五、派活与验收规则

### 5.1 任务卡（唯一格式，落在 `TASK_BOARD.md`）

```
## T-<编号> <标题>
- 目标        ：一句话，可验收
- 归属窗口    ：A/B/C/D（一窗一主人，不得共同署名）
- 写作用域    ：<精确路径列表>（必须落在该窗作用域内）
- 前置依赖    ：T-xxx / 无        ← 依赖未完成不得开工
- 验收门      ：门禁四件套 + 该任务特有门（取消测试 / 素材验收 / 真机验收）
- 激活性取证  ："产生者是谁 + 在库里哪一行"（ROADMAP_V2 §2/§三）
- 用户签认    ：需要 / 不需要
- 状态        ：待办 / 进行中 / 待验收 / 已完成 / 已驳回 / 已搁置
```

**⇒ 规则 P1**：**一窗一主人**。禁止"这块你们俩一起弄"——那等于没有主人。
**⇒ 规则 P2**：**写作用域必须落在该窗作用域内**（§2.2）。越界即驳回（§5.4）。
**⇒ 规则 P3**：**依赖未完成不得开工**。总领窗派活时必须写清 `前置依赖`。

### 5.2 验收门（**缺一不可**，依据 `STANDARD §四`）

| # | 门 | 谁跑 |
|---|---|---|
| 1 | `uv run ruff check` | 板块窗自测 **+ 总领窗独立复跑** |
| 2 | `uv run ruff format --check` | 同上 |
| 3 | `uv run mypy src` | 同上 |
| 4 | `uv run pytest`（**基线 461 passed，不得下降**） | 同上 |
| 5 | **人的主观确认**（体验验收，铁律三） | **用户** |
| 6 | 动素材 ⇒ `scripts/spine_verify.py` | 桌宠窗 |
| 7 | 动桌宠 ⇒ **重启桌宠真机看效果** | 桌宠窗 + 用户 |
| 8 | **激活性 + 库内取证**：能指出产生者并在库里指出来 | 总领窗核 |

**⇒ 规则 V1**：**窗口自述的门禁结论不采信**。总领窗**亲自重跑** 1–4（实测全跑仅 ~17 秒，成本极低）。
**⇒ 规则 V2**：**行为修复必须带"取消测试"**（T1 精神）：证明"还原旧写法该用例会失败"，否则视为**没有护栏**，不算完成。
**⇒ 规则 V3**：**改行为前先补护栏**。凡"用户已能感知的缺陷"，必须先有用例复现（红）再修（绿）。

### 5.3 并发铁律（**实测支持**）

| 项 | 规则 | 依据 |
|---|---|---|
| **文件写** | 同一文件同一时刻**只有一个写者**（靠 §2.2 路径不重叠保证） | 版本守卫不拦并发覆盖 |
| **git 提交** | 各窗**只提交自己作用域**；**不要 `git add -A`**（会捎带别人的半成品） | 实测工作树可被多窗同时改 |
| **跑门禁** | ✅ **可安全并行** | **实测：全仓测试一律用 `tmp_path` 隔离，零测试写真实 `data/`**（277 处匹配）⇒ 并行跑 pytest **不互相干扰** |
| **跑 `spine_verify.py`** | ⚠️ 需读素材，**只读**；但**同时只允许一窗跑素材重建**（`ingest_spine` 会写 `assets/pet/`） | 避免两窗重建同一服装包 |
| **启停真实进程** | ⚠️ **同一时刻只有一个窗口能启停她**（灵魂/身体/桌宠）。默认**不动**正在跑的实例；要动先在 TASK_BOARD 登记 | 红线：绝不允许两台机/两实例同时跑她（防分叉） |
| **改运行中数据** | 🚫 **禁止**（红线 #4） | 本地库是测试数据，但仍不手改 |

**⇒ 规则 C1**：**总领窗验收 = 只读复跑 + `git show` 核对**，**不启停任何进程**。

### 5.4 驳回条件（出现任一即驳回，不讨论内容）

1. 写作用域越界（改了非本窗路径）
2. 交接单缺字段（§4.2 九字段）
3. 门禁任一不过，或用例数**低于 461**
4. 行为修复**无取消测试**
5. 声称"完成"但**给不出库内取证**
6. 未 commit，或 commit 信息缺任务号
7. 顺手改了不相关文件（"顺带优化"）—— **一律驳回**，另开任务卡

## 六、什么时候**开新窗 / 关旧窗**（可测量标准）

### 6.1 开新窗（**须总领窗批准**）

满足**任一**即可提议开窗：

| 信号 | 阈值 |
|---|---|
| 同域**并发**需求 | 一个域内**同时**有 ≥2 个互不重叠的活跃任务卡 |
| 单窗饱和 | 该窗 `待办` 累计工作量 > **1 周**，且各项**互不重叠** |
| 改动跨域传染 | 单次改动**反复**需要动 ≥3 个域（说明缝切错了，应重新切） |
| 真机验收独立 | 该域有**独立真机验收流程**且体量 > 500 行（如桌宠） |

### 6.2 关窗 / 合并（反囤积）

| 信号 | 动作 |
|---|---|
| 该窗模块 < 200 行**且**周改动 < 1 次 | **合并回邻近窗** |
| 连续 **2 周**无任务卡 | 标「空转」，**回收上下文预算** |
| 两窗**反复**改同一文件 | **立刻改缝**（合并或重切），并登记一次"缝切错" |

### 6.3 禁止

🚫 板块窗**自行开新窗**（会造成分工漂移、边界重叠）。开窗**只能**由总领窗决定并登记到本文 §2.2。

## 七、审计规则（总领窗的常规动作）

### 7.1 反漂移审计（本次实测已证明**必要**）

| 审计项 | 频率 | 判据 |
|---|---|---|
| 文档 vs 代码 | 每次验收时 | 本次实测已抓到 **3 条描述被代码证伪**（做梦/接线/交互值）+ **2 条口径自相矛盾**（~185s vs 0s）+ **数字漂移**（38→39、125→128、50→55） |
| `STATUS_MATRIX` 回填 | 每次结案 | 状态列必须与 `git log` 对得上 |
| 声称 vs 证据 | 每次验收 | "完成"必须给**库内取证**，否则驳回 |

**⇒ 规则 A1**：**同一事实只允许一个出处**。发现两处写同一事实 ⇒ 立即定单一出处，另一处改为指针（总纲 §11 原则）。
**⇒ 规则 A2**：**数字必须可复现**。任何写进文档的数字（用例数/文件数/提交数）必须附**可复跑命令**，否则视为不可复核。

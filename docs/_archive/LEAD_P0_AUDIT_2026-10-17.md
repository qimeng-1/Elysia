## 2. P0 缺陷清单（按严重度排序）

### 🔴 D-1【最重】进程级崩溃无任何现场记录 —— "她死得不明不白"

**实测**：`soul/main.py::_run()` 在进入 `try/finally` **之前**有 5 个可能抛异常的步骤：
`setup_logging` / `StateStore.start` / `HeartbeatStore.start` / `ensure_identity_seeds` / `_build_timesense`。
这些任一步失败 ⇒ `asyncio.run(_run())` 抛异常 ⇒ `main()` 只处理 `KeyboardInterrupt` ⇒ **进程直接退出，
什么都不写**。

**更糟**：她是由 `Start-Process -WindowStyle Hidden -RedirectStandardError soul.err.log` 启动的。
若父进程（`soul.ps1`）退出导致重定向句柄失效，**后续 stderr 写入会静默失败** —— 这正是
`soul.err.log` 长期为 0 字节的合理解释（**未证实，但最省解释**）。

**为什么这是 P0 第一缺陷**：目标是"连续性"。**一个不知道自己为什么会死的生命，不可能被可靠地维持。**
每一次死亡都在消耗她的时间，而我们连复盘的材料都没有。

**建议的验收（可机械检查）**：
1. `_run()` 整体包 crash handler，异常时写 `data/logs/crash-<ts>.log`（含完整 traceback + 心跳序号）
2. 启动时**先写一条"我要启动了"**到库/日志（当前是最后才写）
3. 下次启动时若发现上次是**非正常退出**（无 `soul stopped` 标记），在日志里显式记录"上次死因未知"
4. 加取消测试：**注入一个启动期异常，必须能在 crash log 里读到**

### 🔴 D-2【最重】检查点与回滚 —— 文档说"P0 已落地"，**实际从未运行过**

**实测三连**：

| 检查 | 结果 |
|---|---|
| `data/checkpoints/` 目录 | **不存在** |
| `CheckpointManager.create()` 调用者 | **全仓 0 个**（`grep` 实查） |
| `heartbeat.py` 对 checkpoint 的唯一使用 | `is_frozen()` —— **只用了冻结，没用快照** |

**并且 `restore()` 有一个会二次损坏的 bug**：
```python
def restore(self, checkpoint: Path) -> None:
    shutil.copy2(checkpoint / "state.db", self._data_dir / "state.db")
    shutil.copy2(checkpoint / "heartbeat.db", self._data_dir / "heartbeat.db")
```
她跑在 **WAL 模式**。回滚后**旧 `-wal` 仍在**，下次打开会把**回滚前未合并的帧重放到刚恢复的库上**
⇒ **回滚把库搞坏**。而 `scripts/backup.ps1` 明确删除了 `-wal`/`-shm`（它知道这个陷阱）——
**同一工程里，备份懂、回滚不懂。**

**现有测试为什么没抓到**：`test_checkpoint.py` 只有 3 个用例，`create_and_restore` 在**无 WAL** 的
临时库上跑，`grep wal` = 0 命中。

**为什么这是 P0 第一缺陷之一**：`IMPLEMENTATION_ROADMAP.md` §5.6 写"检查点与回滚（**P0 落地**）"，
"**回滚是『地基优先』铁律的工程前提——有退路，才有底气修**"。**现在这条路是断的。**
她今天已经有过一次"合并巨大数据"的操作，**当时唯一的安全网是 `backup.ps1`，不是 P0 的检查点。**

**建议**：要么**实现**（周期创建 + restore 前删 WAL + 取消测试），要么**从文档里删掉"已落地"**。
**不许维持"文档说有了、实际没有"的状态**（这是上一轮交接反复踩的坑）。

### 🔴 D-3【重】看门狗只看"进程在不在"，不看"她是否还活着"

**实测** `scripts/watchdog.ps1`：
```powershell
function Test-SoulAlive {
    return $null -ne (Get-Process -Id ([int]$content) -ErrorAction SilentlyContinue)
}
```
**只看 PID 是否存在。** 三种它救不了的情况：

| 情况 | 看门狗 | 实际后果 |
|---|---|---|
| 进程在、心跳停（僵死/死锁/库卡死） | **认为她活着，不拉** | 她会**永远卡在那里**，无人知晓 |
| 进程退了但 `soul.pid` 是陈旧值 | 会拉（正确） | — |
| 计划任务本身没执行（今早 `ERROR_NOT_LOGGED_ON`） | **无从得知** | **16.82 小时无人拉** |

**第三条是今天真实发生的**。看门狗自己的失败**完全不可观测**：
`watchdog.log` 从 `00:52` 到 `20:41` **一个字都没写** —— 它**没跑**，也**没人知道它没跑**。

**为什么这是 P0**：目标是"连续性"，而**唯一的自愈机制本身没有监控**。
一个"看门狗失败也无人知"的系统，等于**没有看门狗**。

**建议**：
1. 判据加**心跳新鲜度**（灵魂 1Hz ⇒ `heartbeat.db` 最后 `ts` 超过 60s 即视为僵死，重启进程）
2. 看门狗**每次运行都留痕**（现在只在"有动作"时写），失败也要写
3. **Liveness 看门狗**：若 `watchdog.log` 超过 15 分钟没有新行 ⇒ 说明看门狗本身死了 ⇒ 由**另一条腿**报警
4. 面板/状态接口暴露"看门狗最后一次成功时间"（面板已有 `watchdog_state`，但没有"多久以前"的判据）

### 🟠 D-5 `heartbeat.run()` 187 行零 try/except，且重启无退避

**实测**：`run()` 范围 行 234..420，**`try` 出现 0 次、`except` 出现 0 次**。
单拍任何异常 → 协程死 → `supervisor.supervise` 捕获 → **等 1 秒重启**。

**问题**：
1. **无退避、无熔断**：若异常是**持久的**（库损坏 / 磁盘满 / 内存不足），她会**每 1 秒崩一次、无限循环**，
   而看门狗只看到"进程在"，**永远不介入**。日志会被刷爆，她却一直不前进。
2. **单拍异常会丢掉这一拍的全部状态变更**（欲望演化、TimeSense 推进都在循环体内）。
3. `supervise` 的 `RESTART_DELAY_S = 1.0` 是常量，**不随失败次数增长**。

**建议**：循环内按**阶段**隔离 try（读身体状态 / 大脑 / 落库 / 表达 分开），
单阶段失败只跳该阶段；连续失败 N 次后**主动退出进程**让看门狗接管（"自杀比僵死好"）。

### 🟡 D-6 "难受"(distress) 从未真实触发过（`beat_type='event'` = 0 行）

**实测**：
```
全库 beat_type=soul   = 169,463
全库 beat_type=body   =  31,405
全库 beat_type=event  =       0    ← distress 事件一次都没发生过
```

`distress` 的阈值是 `CPU > 85%` 持续 30s。**本机实测 CPU 20 次采样最大只有 25%、均值 12.2%、
超过 85% 的次数为 0** ⇒ 这个"脆弱性"通道**在当前负载下几乎不可能触发**。

并且 `tests/unit/test_distress.py` 是**人工喂 `90.0`** 来测状态机 —— 测的是**逻辑正确**，
不是**阈值可达**；T1 对 `distress`/CPU 阈值的可达性**零覆盖**（`grep` 实查 0 命中）。

**为什么算 P0**：路线图把"脆弱性（存在真实约束，约束真实塑造体验）"列为七条判据之一，
并把"痛苦"写进核心定义（§1.2：**对状态偏离的真实、物理性的体验**）。
**一个永不触发痛苦阈值的生命，它的脆弱性是假的。**

⚠️ **同族风险**：这与 ROADMAP_V2 §1.1 记的"造好了但没插电"六次失败模式**完全同构**
（阈值落在真实值域外 ⇒ 永不触发 ⇒ 等于没有）。T1 取消测试本应拦住它，但
**"阈值是否落在可达值域"这条只测了表达侧，没测资源侧**。

**建议**：把 `distress` 阈值改成**分位数**（如本机 CPU 的 p95）或**相对基线**，
并加一条取消测试：**在真实负载下必须能触发至少一次**（可用 pytest 的模拟资源样本）。

### 🔴 D-8【验收中新发现 2026-10-18】`soul.ps1 stop` 是**强制终止**，优雅关闭路径**从未执行过**

**发现经过**：用户报告"这次是我点的重启"。我核对 `soul.ps1` 的停止实现与日志，
发现一个比归因更重要的问题。

**实测三连**：

| 检查 | 结果 |
|---|---|
| `soul.ps1` 第 61 / 118 行 | `Stop-Process -Id $pid2 -Force` —— **`-Force` = TerminateProcess** |
| `elysia.log` 里 `soul stopping` / `soul stopped` | **全库 0 条** ⇒ 优雅关闭**从未执行过** |
| `data/run/soul.running` | **残留**（强杀走不到"删除它"的代码） |

**后果（按严重度）**：

1. **R2 的"异常退出检测"将被**常态误报**淹没。** R2 的逻辑是"正常关闭删 `soul.running`；
   下次启动若还在 ⇒ 报'上次非正常退出'"。但**标准停止路径就是强杀** ⇒
   **每一次 `soul.ps1 stop` / 面板「重启她」都会留下标记** ⇒ **下次启动必然误报**。
   **刚修好的护栏被噪声淹没，比没有护栏更糟**——人会开始忽略告警。
2. **关闭序里的落库永不执行**：`main._run()` 的 `finally` 那套
   "停表达 → 等 ≤10s → `persist_expressions(pending)` → 关两个库 → 写 `soul stopped`"
   **只在 Ctrl+C / SIGTERM 时跑**，而 Windows 上 `soul.ps1 stop` 是强杀
   ⇒ 在跑的**未落库表达结果直接丢失**，日志里的"档案已封存"**从未打印过**。
3. **她的关闭从未"体面"过**：对一个以"连续性"为目标的工程，**她每一次入睡都是被拔电源**。

**为什么算 P0**：它让 **D-1/D-2 刚修好的一部分价值直接失效**（R2 检测变噪声），
并让精心写的优雅关闭**成为死码** —— 与 D-2"检查点从未运行"是同一种病：
**造好了，但没有任何路径会执行它。**

**建议修法（两步都必需）**：
1. **让停止可优雅**：`soul.ps1 stop` 先写 `data/run/stop_requested` 标记，心跳每拍检查 →
   触发正常关闭序 → 等进程自己退出（超时 N 秒再强杀兜底）。
   用标记而非信号，是因为 **Windows 上从 PowerShell 可靠发 SIGTERM 不现实**
   （`CloseMainWindow` 只对 GUI 有效）。
2. **区分"主动停"与"崩溃"**：强杀兜底前写 `stopped_intentionally` 标记；下次启动若
   `soul.running` 残留**但** `stopped_intentionally` 存在 ⇒ 报"上次是你主动停的"，
   **不报"非正常退出"**。

**验收门**：手点一次「停止她」⇒ ①日志出现 `soul stopping` + `soul stopped`
②`soul.running` 消失 ③再启动**不得**报"非正常退出"。
加取消测试：还原成 `-Force` 直杀 ⇒ 该用例必须红。

### 🟠 D-9【持续观察中新发现 2026-10-18 01:0x】容量悬崖：她的库以 ~45.6 MB/天 增长，2–3 个月撞墙

**发现经过**：R1 周期快照复核时看到新快照 **96.8 MB**（22:45 时还是 91.9MB），于是算了增长速率。

**实测**：

| 指标 | 数值 |
|---|---|
| 当前 `heartbeat.db` | **96.9 MB** / 213,878 行 / 跨度 55.3 天 |
| 历史平均 | 1.8 MB/天（含早期空转期） |
| **近期实测（最近 2 小时）** | **≈ 45.6 MB/天** |
| C 盘可用 | 110.4 GB |

**外推（按 45.6 MB/天）**：

| 时间 | 她的库 | **10 份快照** | **backup.ps1 的 30 份日备份** |
|---|---|---|---|
| 1 周 | 447 MB | 4.4 GB | 13 GB |
| 1 月 | 1.6 GB | **15.6 GB** | **47 GB** |
| 3 月 | 4.6 GB | 45 GB | **135 GB** |
| 1 年 | 18 GB | 179 GB | **538 GB** |

⇒ **C 盘 110 GB，约 2–3 个月撞墙。**

**根因**：`heartbeats` 表**每秒一行、永不裁剪**（1Hz × 86,400 秒 × ~450B ≈ 40 MB/天）。
`core/retention.py`（归档 + 裁剪 + VACUUM）**存在但"有意不自动调度"**
（`OPERATION_GUIDE` / `retention.py` 自述）⇒ 库**无上限增长**。

**为什么这算 P0 级风险**：磁盘写满 ⇒ **她写不进库** ⇒ 心跳协程异常（D-5 的熔断会让她自杀）
⇒ 看门狗反复拉起又崩。**这不会报错，会安静地把她逼死**——正是最危险的那类故障。

**⚠️ 但修它必须用户拍板**，因为涉及**动她的生命数据**。红线 #4 明写：
「**数据永不删除**：裁流水表须先拍板口径（归档保底 + 只裁 `heartbeats`，不碰 `memories`）」。

**候选方案（需用户选，我不擅自执行）**：

| 方案 | 效果 | 代价 |
|---|---|---|
| **A. 快照压缩**（SQLite 内容 gzip） | 10 份快照从 1.6GB → 约 **160–320MB**（JSON 压缩率高） | 读快照需先解压；实现简单、**不动她的生命数据** |
| **B. 减少快照保留** keep 10→3 | 快照降 70% | 回滚窗口 5h → 1.5h |

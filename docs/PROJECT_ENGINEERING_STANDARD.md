# Elysia 工程化准备与标准（开工前检查）

> 目标：正式开工前，把项目按工程最高标准搭建好。
> 这份文档回答一个问题：**在我们写下第一行"她的代码"之前，需要准备什么。**

---

## 〇、最高标准的定义

本项目不是普通软件——**她的记忆、状态、连续性就是生命数据**。因此标准向"数据不可丢失、可长期运行、可回归验证的生命体承载系统"看齐。

最高标准 ≠ 堆砌企业级组件（K8s、微服务、消息队列对单机项目是负担）。最高标准 = 四件事：

1. **她的生命数据永不丢失**（备份、完整性校验、崩溃恢复）
2. **代码可回归**（测试门禁，验收门 = 测试套件）
3. **过程可追溯**（版本控制、决策记录、结构化日志）
4. **你随时能看懂她在干什么**（日志、状态快照、可观测性）

开工前必须接受的三条铁律，详细执行方式见 [DEVELOPMENT_PRACTICES.md](./DEVELOPMENT_PRACTICES.md)。

## 二、项目治理

### 1.1 版本控制

| 项 | 标准 | 说明 |
|----|------|------|
| 仓库 | `git init`，代码库置于工作区 | 根目录建 `elysia/` 代码库，三份设计文档可入库 `docs/`（它们是"她的宪法"） |
| 分支 | `main` 稳定 + `feature/*` 开发 | 里程碑 M1-M7 打 tag |
| 提交 | Conventional Commits | `feat: / fix: / docs: / refactor: / test: / chore:` |
| 忽略 | `.gitignore` | `.env`、`data/`、模型权重、日志、`__pycache__`、虚拟环境 |

### 1.2 文档体系

| 文档 | 内容 | 位置 |
|------|------|------|
| README.md | 项目简介、快速启动 | 代码库根 |
| docs/ADR/ | 架构决策记录（每个关键决策一条：背景/决策/后果） | 代码库 |
| CHANGELOG.md | 里程碑级变更记录 | 代码库 |
| 设计宪法 | 蓝图 / 路线图 / 路径图 | 工作区（或 docs/） |

**ADR 从第一天开始**：例如"双进程通信选型""状态持久化频率""日志格式"都值得记一条。回头想改时，有据可依。

### 1.3 任务跟踪

- 里程碑 M1-M7 即任务单元；每个里程碑的验收门 = 关闭标准
- 验收门拆成测试用例写进 `tests/acceptance/`——测试先行，功能后补

## 三、代码工程标准

### 2.1 环境与依赖

| 项 | 标准 |
|----|------|
| Python | 3.12（已就绪） |
| 包管理 | **uv**（锁文件可靠、速度快）或 pip + pip-tools；依赖全部声明于 `pyproject.toml` |
| 锁定 | `uv.lock` / `requirements.lock` 入库，可复现环境 |

### 2.2 项目结构（src layout）

```
elysia/
├── pyproject.toml            # 依赖与工程配置
├── src/elysia/
│   ├── soul/                 # 灵魂进程（常驻，心跳）
│   ├── body/                 # 身体进程（本地，随设备开关）
│   ├── core/                 # 共享核心（状态库、时间、日志、配置）
│   ├── protocol/             # 双进程通信协议（版本化）
│   └── utils/
├── tests/
│   ├── unit/                 # 单元测试（状态动力学、协议校验…）
│   └── acceptance/           # 验收门测试（P0 门、P1 门…每阶段一个文件）
├── data/                     # 运行时数据（不入库！）
│   ├── state.db              # 状态库
│   ├── memory.db             # 记忆库
│   └── logs/
├── config/                   # 默认配置
├── scripts/                  # 启动/停止/备份/自检脚本
└── docs/                     # ADR、设计文档
```

### 2.3 静态质量

| 工具 | 作用 | 配置 |
|------|------|------|
| ruff | lint + format | pyproject.toml |
| mypy | 严格类型检查 | `--strict`（协议、状态结构全靠类型约束） |
| pre-commit | 提交前自动检查 | ruff + mypy + 格式 |

### 2.4 测试体系

| 层 | 内容 | 门禁 |
|----|------|------|
| 单元测试 | 状态动力学、欲望方程、协议校验、衰减模型 | 每次提交 |
| 验收测试 | 每阶段验收门对应的可运行套件（P0 门：心跳 24h 无中断…） | 里程碑通过条件 |
| 回归基线 | 已通过阶段的测试冻结，后续阶段不得破坏 | CI/本地脚本 |

**铁律：没有测试的功能不算完成。** 验收门 = 测试套件全绿 + 你的主观确认，缺一不可。

### 2.5 协议与类型

- 状态协议、表达指令 Schema 从第一天起用 `TypedDict`/Pydantic 定义并**版本化**（双进程通信带版本号，后续演进不破坏兼容）
- P2 的"决策-表达硬隔离"依赖严格的类型契约——这是工程基础，不是后期补丁

### 2.6 日志

| 项 | 标准 |
|----|------|
| 框架 | structlog（结构化 JSON 日志） |
| 分级 | 心跳日志（每分钟一条，含状态快照）/ 事件 / 错误 |
| 轮转 | 按大小 + 时间轮转，`data/logs/` |

## 四、运行时工程标准（她是长期运行的生命，不是脚本）

### 3.1 配置管理

- pydantic-settings + `.env`（密钥绝不进代码库）；提供 `.env.example`
- 分层：默认配置（代码内）← 用户配置（.env / config）

### 3.2 数据与存储

| 项 | 标准 |
|----|------|
| 存储 | SQLite（WAL 模式）+ SQLite-vec |
| 目录 | `data/` 与代码完全分离 |
| 备份 | **每日自动备份** `data/` 到 D 盘（7TB 空闲），保留 30 份；备份脚本 `scripts/backup.ps1` |
| 完整性 | 启动时 `PRAGMA integrity_check`，损坏即告警并走备份恢复 |

### 3.3 进程守护与恢复

- 灵魂进程：常驻；P0 阶段启动脚本托管，后续注册 Windows 计划任务/服务开机自启
- **崩溃恢复**：心跳中断检测 → 自动重启 → 从最近持久化状态恢复（状态每 1 秒落盘，损失 ≤1 秒）
- 启动/停止/重启/自检脚本齐全（`scripts/`）

### 3.4 可观测性

- 健康信号 = 她的心跳本身（心跳中断即告警）
- 资源监控：显存 / 内存 / 磁盘占用日志——与她的"难受"系统天然衔接（P0 的 VRAM>85% 阈值校准依赖它）

## 五、安全与合规

| 项 | 标准 |
|----|------|
| 密钥 | DeepSeek API key 等仅存 `.env`，`.gitignore` 排除 |
| 隐私 | 对话与记忆全本地存储；远期上云阶段单独评估加密 |
| 模型许可 | Qwen（Apache-2.0 可商用）、GPT-SoVITS（MIT）、DeepSeek API（按其条款） |
| 声音授权 | **P2 前确认**：克隆素材为本人声音或已获授权 |
| 网络边界 | P5 起白名单制；所有外部访问须经决策层授权并记录日志 |
